## 1. Why Keys Matter

Every `MERGE` line raises one question: **"Does this record already exist?"**

```
MERGE line arrives
      │
      ▼
 HDL resolves the KEY on the line
      │
  ┌───┴─────────────┐
  │ Record found?   │
  └───┬─────────┬───┘
     Yes        No
      │          │
   UPDATE     CREATE
```

Keys are used in **two places** on every line:

| Use | Meaning | Example |
|---|---|---|
| **Local key** | Identifies *the record on this line* | `SourceSystemOwner=LEGACY`, `SourceSystemId=EMP1001_ASG` |
| **Foreign key / reference** | Identifies *another record this line points to* (parent or lookup-like object) | `WorkTermsAssignmentId(SourceSystemId)=EMP1001_WT`, `JobCode=SE01` |

**Wrong key = wrong outcome.** A bad key can create duplicates (a second "Ravi Sharma"), update the wrong person, or fail with "record not found".

## 2. The Four Key Types at a Glance

HDL supports four key types for integration-enabled business objects:

| Key Type | What it is | Generated by | Data type | Use on **Create**? | Use on **Update**? | Stored where |
|---|---|---|---|---|---|---|
| **Oracle Fusion GUID** | Globally unique identifier | Oracle (auto) | Hexadecimal | ❌ No | ✅ Yes | Integration Key Map (not on the object) |
| **Oracle Fusion Surrogate ID** | Internal numeric primary key | Oracle (auto) | Numeric | ❌ No | ✅ Yes | **On the object** (e.g. `PERSON_ID`) + Key Map |
| **Source Key** | Your source system's ID (Owner + Id) | **You** (or a default) | Alphanumeric | ✅ Yes | ✅ Yes | Integration Key Map (not on the object) |
| **User Key** | Natural, human-readable business key | **You** / user | Alphanumeric | ✅ Yes | ✅ Yes (with care) | **On the object** (e.g. `PERSON_NUMBER`) |

**Simple memory hook:**
- **System keys** (GUID, Surrogate ID): Oracle makes them, so they don't exist until the record is created. **They can't be used to create.**
- **Your keys** (Source Key, User Key): you supply them, so **they can be used to create.**

> Oracle's tip: **whenever possible, use source keys for both creating and updating business objects.**

## 3. Oracle Fusion Surrogate ID

### What it is
The **internal numeric primary key** Oracle generates when a record is created. It's the `..._ID` column you see in tables.

| Object | Surrogate ID column |
|---|---|
| Person | `PER_ALL_PEOPLE_F.PERSON_ID` |
| Assignment | `PER_ALL_ASSIGNMENTS_M.ASSIGNMENT_ID` |
| Work Relationship | `PER_PERIODS_OF_SERVICE.PERIOD_OF_SERVICE_ID` |
| Job | `PER_JOBS_F.JOB_ID` |
| Location | `HR_LOCATIONS_ALL.LOCATION_ID` |

### Characteristics
- **Numeric**, e.g. `300000001572671`
- **Unique only within its object type** (a Job and a Location could, in theory, share an ID value)
- **Held on the object itself**, and also used in the Integration Key Map to map GUIDs and source keys
- Every object has one, even objects that aren't integration-enabled
- **Can't be used on create**: it doesn't exist yet

### Example: update a job using its surrogate ID
```
METADATA|Job|JobId|EffectiveStartDate|Name
MERGE|Job|300000001234567|2026/04/01|Senior Software Engineer
```

### Pros & cons
| ✅ Pros | ❌ Cons |
|---|---|
| Exact, never changes | Not visible to business users; you need SQL/BIP to find it |
| Good for one-off fixes from extracts | Differs between environments (DEV ≠ TEST ≠ PROD) |
| | Not available for creates |

> **Interview point:** surrogate IDs **differ per environment**. A file built with TEST IDs won't work in PROD. Source keys and user keys are portable.

## 4. Oracle Fusion GUID

### What it is
A **hexadecimal globally unique identifier** that Oracle generates when the record is created.

### Characteristics
- **Hexadecimal**, e.g. `88ABCD164738983...`
- **Unique across all objects** (unlike surrogate IDs)
- **Not held on the object.** It lives in the **Integration Key Map** table.
- **Can't be used on create**
- **Highest precedence** in key resolution (Section 7)

### Example: update using a GUID
```
METADATA|Location|GUID|EffectiveStartDate|LocationName
MERGE|Location|88ABCD164738983F2E1A|2026/04/01|Chennai Office – Tower B
```

### When it's used
Rarely by hand. Mainly in **system-to-system integrations** where a downstream system received GUIDs (e.g. from an extract) and sends updates back.

## 5. Source Keys (Recommended)

### What it is
A source key identifies a record **as it is known in the source system** (SAP, PeopleSoft, EBS, a recruiting tool, a spreadsheet). It has **two parts**:

| Attribute | Meaning | Example |
|---|---|---|
| `SourceSystemOwner` | **Which** source system the data comes from | `LEGACY`, `SAP`, `PSFT`, `TALEO` |
| `SourceSystemId` | The record's **unique ID** in that source | `EMP1001`, `EMP1001_ASG`, `LOC_CHN_01` |

**Owner + Id together** must be unique for a component.

### Rule 1: register the owner first
`SourceSystemOwner` is **validated against the `HRC_SOURCE_SYSTEM_OWNER` lookup type**. Add your source-system names to it (*Setup and Maintenance → Manage Common Lookups*) **before** loading. Otherwise the load fails on an invalid owner.

### Rule 2: only integration-enabled objects
Source keys work only for **integration-enabled business objects**. The business-object documentation / View Business Objects shows which ones are.

### Rule 3: not stored on the record
Source keys **aren't held on the created record**. They exist in the **Integration Key Map** table (Section 9).

### Rule 4: default source keys
If you create a record **without** a source key, Oracle generates a **default source key**:
- `SourceSystemOwner` = **`FUSION`**
- `SourceSystemId` = **the surrogate ID**

So a job created in the UI (job ID `300000001234567`) can still be referenced as `FUSION` + `300000001234567`. You can later replace that default with your own key using `SourceKey.dat` (Section 10).

### Rule 5: one source key per component record
Every **component** gets its **own** source key, not just the top-level object:

```
Worker                 LEGACY | EMP1001
 ├─ PersonName         LEGACY | EMP1001_NAME_GLOBAL
 ├─ PersonEmail (work) LEGACY | EMP1001_EMAIL_W1
 ├─ PersonPhone (work) LEGACY | EMP1001_PH_W1
 └─ WorkRelationship   LEGACY | EMP1001_WR_01
      └─ WorkTerms     LEGACY | EMP1001_WT_01
           └─ Assignment LEGACY | EMP1001_ASG_01
```

### Rule 6: date-effective objects use ONE source key for all date splits
The source key identifies the **record**, not each historical row. All date-effective changes for the same assignment share one source key:

```
METADATA|Assignment|SourceSystemOwner|SourceSystemId|EffectiveStartDate|EffectiveEndDate|EffectiveSequence|EffectiveLatestChange|ActionCode|DepartmentName
MERGE|Assignment|LEGACY|EMP1001_ASG_01|2024/01/01|2025/03/31|1|Y|HIRE|Sales
MERGE|Assignment|LEGACY|EMP1001_ASG_01|2025/04/01|4712/12/31|1|Y|TRANSFER|Marketing
```
*(Abbreviated: real assignment lines need more attributes.)*

### Source key design: do's and don'ts
| ✅ Do | ❌ Don't |
|---|---|
| Use stable IDs that never change in the source (employee ID, legacy row ID) | Include **effective dates or hire date** in the key |
| Use a clear convention: `<EmpID>_<Component>_<Type>`, e.g. `EMP1001_EMAIL_W1` | Include **first or last names** (they change on marriage, corrections) |
| Keep keys unique per component | Reuse one ID across different components without suffixes |
| Keep one owner per source system | Mix owners randomly for the same data |
| Document the convention for the whole project | Let each developer invent their own pattern |

> **Bottom line:** don't design keys from values that can easily change in the source application.

### Why source keys are recommended
- **Portable** across DEV/TEST/PROD (you control them)
- **Traceable** back to the source system record
- **Stable**: business values like names and codes can change, your IDs don't
- **Usable for create and update**, so one file works whether or not the record exists

## 6. User Keys

### What it is
A **user key** (also called a **natural key**) is one or more **business attributes** that uniquely identify a record and are **visible in the UI**.

### Examples (illustrative; confirm in View Business Objects)
| Object | User key attribute(s) |
|---|---|
| Worker (Person) | `PersonNumber` |
| Assignment | `AssignmentNumber` |
| Job | `SetCode` + `JobCode` |
| Location | `SetCode` + `LocationCode` |
| Grade | `SetCode` + `GradeCode` |
| Work Relationship | `PersonNumber` + `LegalEmployerName` + `DateStart` (combination) |

### Characteristics
- **Held on the object** (e.g. `PERSON_NUMBER` column)
- Can be **one or many attributes** (composite)
- Sometimes there are **alternative** user keys for one object
- **Some user keys can be updated**, e.g. an organization or location *name*
- Usually required on create (unless Oracle generates the value, e.g. automatic person numbering)

### Example: create and update a job with user keys only
```
METADATA|Job|SetCode|JobCode|EffectiveStartDate|EffectiveEndDate|Name
MERGE|Job|COMMON|SE01|2020/01/01|4712/12/31|Software Engineer
```
Running the same line later with a different `Name` **updates** the job, because `COMMON` + `SE01` already exists.

### The weakness of user keys
Because some user keys **can change**, you **can't use user keys alone to update some objects**. Example: if a department was renamed from "Engineering" to "Product Engineering", a file still sending `DepartmentName = Engineering` won't find it. Historical references break.

### When to use user keys
- Records were **created in the UI** (no source key known) and you don't want to replace the default source keys
- **One-off loads** or quick fixes
- Referencing **setup objects** that are well known by code (Job code, Location code)

## 7. Key Resolution Order (Precedence)

If a line contains **more than one** key type, HDL resolves them in this fixed order:

```
1. Oracle Fusion GUID        ← highest priority
2. Source Key
3. Oracle Fusion Surrogate ID
4. User Key                  ← lowest priority
```

**Memory trick: "G-S-S-U" — "Good Source Saves yoU."**

### No cross-validation (a common trick question)
HDL uses the **first** key it finds in that order and **ignores the rest**. It does **not** check that they agree.

> Example: you supply a **GUID** that points to Job A, and a **source key** that points to Job B. HDL uses the GUID and **updates Job A**. The source key is ignored and **no error is raised**.

**Lesson:** don't send several conflicting keys "just to be safe". Send **one** key type per record, consistently.

### Worked example
```
METADATA|Job|SourceSystemOwner|SourceSystemId|JobId|SetCode|JobCode|EffectiveStartDate|Name
MERGE|Job|LEGACY|JOB_SE01|300000009999999|COMMON|SE01|2026/04/01|Software Engineer II
```
Which key does HDL use? → **Source key** (`LEGACY` + `JOB_SE01`), because it ranks above the surrogate ID (`JobId`) and the user key (`SetCode` + `JobCode`). Even if `JobId` belongs to a different job, there's no error.

## 8. Local Keys vs Foreign-Object References

### Local key: identifies the record on the line
You supply it through **dedicated attributes**:
- Source key → `SourceSystemOwner` + `SourceSystemId`
- GUID → `GUID`
- Surrogate ID → the object's ID attribute (e.g. `JobId` on a Job line)
- User key → its business attributes (e.g. `SetCode` + `JobCode`)

### Foreign reference: points to another record
Used for **parents** (PersonName → Person) and **related objects** (Assignment → Job, Location, Department).

There are three common ways to reference a foreign object:

| Method | METADATA syntax | Example value |
|---|---|---|
| **Source key** (with hint) | `<Attr>Id(SourceSystemId)` | `JobId(SourceSystemId)` → `JOB_SE01` |
| **Surrogate ID** | `<Attr>Id` | `JobId` → `300000001234567` |
| **User key** | the user-key attribute(s) | `JobCode` → `SE01` (+ set code where needed) |

**Example: an Assignment referencing its parent and a Job in three different ways**
```
-- (1) Source keys everywhere (recommended for integrations)
METADATA|Assignment|SourceSystemOwner|SourceSystemId|WorkTermsAssignmentId(SourceSystemId)|JobId(SourceSystemId)|...
MERGE|Assignment|LEGACY|EMP1001_ASG_01|EMP1001_WT_01|JOB_SE01|...

-- (2) Surrogate ID for the job
METADATA|Assignment|SourceSystemOwner|SourceSystemId|WorkTermsAssignmentId(SourceSystemId)|JobId|...
MERGE|Assignment|LEGACY|EMP1001_ASG_01|EMP1001_WT_01|300000001234567|...

-- (3) User key for the job
METADATA|Assignment|SourceSystemOwner|SourceSystemId|WorkTermsAssignmentId(SourceSystemId)|JobCode|...
MERGE|Assignment|LEGACY|EMP1001_ASG_01|EMP1001_WT_01|SE01|...
```

### Rules to remember
1. **You can't use source keys for foreign references unless you also use a source key for the local record.** If your Assignment line has no `SourceSystemOwner`/`SourceSystemId`, you can't write `JobId(SourceSystemId)`.
2. A foreign object can be referenced by source key only if it's **integration-enabled**.
3. The foreign record must **already exist** in Oracle, or be **in the same data set and load earlier**. Source keys, GUIDs and surrogate IDs **aren't recognised until the referenced record exists in Oracle**.
4. With `(SourceSystemId)` references, HDL looks up the foreign record under the **same `SourceSystemOwner`** as the local line by default. Keep one owner per source system to avoid mismatches.
5. Mixing is allowed: source keys for workers and user keys (codes) for setup objects is very common.

## 9. The Integration Key Map Table

### What it is
**`HRC_INTEGRATION_KEY_MAP`** is the table that maps **source keys and GUIDs** to **surrogate IDs**. Source keys and GUIDs **aren't stored on the object**, so this is where they live.

```
 HRC_INTEGRATION_KEY_MAP
 ┌─────────────┬────────────────────┬──────────────────┬─────────────────┬──────────────┐
 │ OBJECT_NAME │ SOURCE_SYSTEM_OWNER│ SOURCE_SYSTEM_ID │ SURROGATE_ID    │ GUID         │
 ├─────────────┼────────────────────┼──────────────────┼─────────────────┼──────────────┤
 │ Location    │ LEGACY             │ LOC_CHN_01       │ 300000008899933 │ 88ABCD16...  │
 │ Person      │ LEGACY             │ EMP1001          │ 300000001572671 │ 7F3E01AB...  │
 │ PersonEmail │ FUSION             │ 300000002451147  │ 300000002451147 │ 1C9D44EE...  │ ← default key
 └─────────────┴────────────────────┴──────────────────┴─────────────────┴──────────────┘
```
*(Values illustrative.)*

### Query it with BIP (read-only)
```sql
SELECT object_name,
       source_system_owner,
       source_system_id,
       surrogate_id,
       RAWTOHEX(guid) AS guid
FROM   hrc_integration_key_map
WHERE  source_system_owner = 'LEGACY'
AND    object_name         = 'Person';
```

### Common uses
| Need | How the key map helps |
|---|---|
| "What source key does person 1001 have?" | Join `SURROGATE_ID` to `PER_ALL_PEOPLE_F.PERSON_ID` |
| "Was this record created by HDL or the UI?" | `FUSION` owner = default key → created without a source key (often UI) |
| Building DELETE / update files | Pull existing source keys or IDs for the records |
| Reconciliation after conversion | Count records per `OBJECT_NAME` + owner vs the legacy counts |

> **Note:** Oracle provides **no standard process to extract source-key information**, so a **BIP query on this table** is the usual approach.

### Example: find source keys for a person's components
```sql
SELECT papf.person_number,
       km.object_name,
       km.source_system_owner,
       km.source_system_id
FROM   per_all_people_f        papf,
       hrc_integration_key_map km
WHERE  km.surrogate_id  = papf.person_id
AND    km.object_name   = 'Person'
AND    papf.person_number = '1001'
AND    TRUNC(SYSDATE) BETWEEN papf.effective_start_date AND papf.effective_end_date;
```
*(Check the exact `OBJECT_NAME` values in your instance: they're the internal object names, not always the `.dat` discriminator.)*

## 10. Changing Source Keys with SourceKey.dat

### When you need it
- Records were created in the **UI** or by Oracle, so they have **default `FUSION` keys**, and you now want a **real source key** for ongoing integration.
- A source key was **loaded wrongly** (typo, wrong convention).
- The **source system changed** (e.g. migrating from `PSFT` to `SAP` IDs).

### The SourceKey business object
You load a `SourceKey.dat` file that names the **object and component**, the **old** key, and the **new** key.

```
METADATA|SourceKey|BusinessObject|Component|OldSourceSystemOwner|OldSourceSystemId|NewSourceSystemOwner|NewSourceSystemId
MERGE|SourceKey|Worker|PersonAddress|FUSION|300000002451147|LEGACY|EMP1001_ADDR_HOME
MERGE|SourceKey|Worker|PersonPhone|FUSION|300000001572671|LEGACY|EMP1001_PH_W1
```

| Attribute | Meaning |
|---|---|
| `BusinessObject` | The business object's file discriminator, e.g. `Worker` |
| `Component` | The component discriminator, e.g. `PersonAddress` |
| `OldSourceSystemOwner` / `OldSourceSystemId` | The current key (`FUSION` + surrogate ID if it's a default) |
| `NewSourceSystemOwner` / `NewSourceSystemId` | The key you want from now on |

### Steps
1. Add the new owner to the **`HRC_SOURCE_SYSTEM_OWNER`** lookup (if it isn't there already).
2. Query **`HRC_INTEGRATION_KEY_MAP`** to get the old keys.
3. Build `SourceKey.dat` → zip → **Import and Load Data**.
4. Re-query the key map to confirm the new keys.
5. From now on, send the **new** keys in all files.

> Don't try to "change" a source key by sending a MERGE with a new SourceSystemId. HDL treats it as a **new** key → **create** → duplicate record (or an error). Always use **SourceKey.dat**.

## 11. Choosing a Key Strategy

### Which key for which operation
| Operation | GUID | Surrogate ID | Source Key | User Key |
|---|---|---|---|---|
| **Create** | ❌ | ❌ | ✅ | ✅ |
| **Update** | ✅ | ✅ | ✅ (best) | ✅ (if the key is stable) |
| **Delete** | ✅ | ✅ | ✅ | ✅ (if stable) |
| **Reference a foreign object** | ✅ | ✅ | ✅ (if local also uses source key) | ✅ |

### Typical project strategy
| Scenario | Recommended approach |
|---|---|
| **Data conversion** from a legacy system | **Source keys** for every object/component (`SourceSystemOwner` = legacy system). Load setup objects with source keys too, so later references are consistent. |
| **Ongoing inbound integration** (3rd-party HR/recruiting) | **Source keys** that match the external system's IDs, so every update finds the right record. |
| **Records originally created in the UI**, now part of an integration | Convert their default `FUSION` keys to real keys with **SourceKey.dat**, or reference them by **user key**. |
| **One-off mass fix** from a BIP extract | **Surrogate IDs** or **user keys** pulled from the extract are fine. |
| **Setup-object references** (job, grade, location) | Source keys if they were loaded with source keys; otherwise **user keys/codes**. |

### Decision flow
```
Is the record being CREATED?
   ├─ Yes → Use SOURCE KEY (preferred) or USER KEY
   └─ No (update/delete) →
         Was it loaded with a source key you know?
            ├─ Yes → Use that SOURCE KEY
            └─ No  → Is the user key stable (e.g. PersonNumber, AssignmentNumber)?
                       ├─ Yes → USER KEY
                       └─ No  → SURROGATE ID / GUID from a BIP extract
                                (or convert to a source key via SourceKey.dat)
```

# PHASE 3 CHEAT SHEET

| Topic | Remember this |
|---|---|
| Four key types | GUID, Surrogate ID, Source Key, User Key |
| Create with | **Source key** or **User key** only |
| Resolution order | **GUID → Source Key → Surrogate ID → User Key** ("Good Source Saves yoU") |
| Cross-validation | **None**: the first key found wins; the others are ignored silently |
| GUID | Hex, unique across all objects, stored in the key map, not on the object |
| Surrogate ID | Numeric, unique per object type, on the object (`PERSON_ID`), differs per environment |
| Source key | `SourceSystemOwner` + `SourceSystemId`; stored in the key map; Oracle's recommendation |
| Owner lookup | `HRC_SOURCE_SYSTEM_OWNER` (Manage Common Lookups), set it up before loading |
| Default source key | Owner `FUSION`, Id = surrogate ID (when no key is supplied on create) |
| Date-effective | One source key per record, shared by all date splits |
| Key design | Stable IDs; never dates or names in the key |
| User keys | Natural keys (PersonNumber, JobCode+SetCode); some can change |
| Foreign reference | `JobId(SourceSystemId)`, `JobId`, or `JobCode` |
| Source-key foreign refs | Allowed only if the local record also uses a source key |
| Key map table | `HRC_INTEGRATION_KEY_MAP` (OBJECT_NAME, SOURCE_SYSTEM_OWNER, SOURCE_SYSTEM_ID, SURROGATE_ID, GUID) |
| Change a source key | `SourceKey.dat`: BusinessObject, Component, Old owner/Id, New owner/Id |

# PRACTICE QUESTIONS & ANSWERS

### Section A — Concept checks

**Q1. Which two key types can't be used when creating a record, and why?**
<details><summary>Answer</summary>

**GUID** and **Surrogate ID**. Oracle generates both only when the record is successfully created, so they don't exist yet at create time.
</details>

**Q2. State the key resolution order.**
<details><summary>Answer</summary>

1. Oracle Fusion **GUID** → 2. **Source key** → 3. Oracle Fusion **Surrogate ID** → 4. **User key**.
</details>

**Q3. Where are source keys and GUIDs stored? Where are surrogate IDs and user keys stored?**
<details><summary>Answer</summary>

Source keys and GUIDs: in the **Integration Key Map** table (`HRC_INTEGRATION_KEY_MAP`), not on the object. Surrogate IDs and user keys: **on the object itself** (e.g. `PER_ALL_PEOPLE_F.PERSON_ID`, `PERSON_NUMBER`). The surrogate ID is also in the key map, as the link.
</details>

**Q4. What two attributes make up a source key, and what must you configure before using them?**
<details><summary>Answer</summary>

`SourceSystemOwner` + `SourceSystemId`. The owner value must be added to the **`HRC_SOURCE_SYSTEM_OWNER`** lookup type (Manage Common Lookups) first.
</details>

**Q5. A job was created in the UI. What is its source key?**
<details><summary>Answer</summary>

A **default source key**: `SourceSystemOwner = FUSION`, `SourceSystemId = <the job's surrogate ID>`.
</details>

**Q6. A worker's assignment has 5 date-effective changes. How many source keys does the assignment have?**
<details><summary>Answer</summary>

**One.** A source key identifies the record, not each date split. All 5 MERGE lines use the same SourceSystemId with different EffectiveStartDates.
</details>

**Q7. Why is a surrogate ID a poor choice for a reusable integration file?**
<details><summary>Answer</summary>

Surrogate IDs are **environment-specific** (DEV/TEST/PROD differ), aren't visible to business users, and can't be used to create. A file built on TEST IDs won't work in PROD.
</details>

**Q8. Why can't user keys alone be used to update some objects?**
<details><summary>Answer</summary>

Some user-key values **can change** (e.g. a department or location name). Once changed, the old value no longer identifies the record, so references break.
</details>

### Section B — Scenario-based (interview style)

**S1. Your file has both a GUID and a source key on a Location line. The GUID points to the Chennai location; the source key points to Bangalore. What happens?**
<details><summary>Answer</summary>

HDL uses the **GUID** (highest precedence) and **updates the Chennai location**. The source key is **ignored** and **no error** is raised, because HDL doesn't cross-validate keys. Lesson: send one consistent key type per record.
</details>

**S2. The load fails with an invalid SourceSystemOwner `SAP_HR`. What's the fix?**
<details><summary>Answer</summary>

Add `SAP_HR` as a lookup code in the **`HRC_SOURCE_SYSTEM_OWNER`** lookup type (*Setup and Maintenance → Manage Common Lookups*), then resubmit the failed objects.
</details>

**S3. A developer used `SourceSystemId = EMP1001_RAVI_SHARMA` for PersonName. What's wrong with this design?**
<details><summary>Answer</summary>

It includes the person's **name**, which can change (marriage, correction). A later file built from the new name would generate a *different* key, so HDL would try to **create** a second name record instead of updating. Use a stable pattern such as `EMP1001_NAME_GLOBAL`.
</details>

**S4. You loaded 1,000 workers last month with owner `LEGACY` and IDs like `E1001`. Now the client wants all ongoing integrations to use owner `WORKDAY` and IDs like `WD-1001`. How do you switch without creating duplicates?**
<details><summary>Answer</summary>

1. Add `WORKDAY` to `HRC_SOURCE_SYSTEM_OWNER`.
2. Pull the existing keys from `HRC_INTEGRATION_KEY_MAP` (owner `LEGACY`) for every component (Person, names, emails, relationships, terms, assignments…).
3. Build a **`SourceKey.dat`** mapping each `Old (LEGACY, E1001…)` to `New (WORKDAY, WD-1001…)` per **BusinessObject + Component**.
4. Load it, verify in the key map, and use only the new keys from then on.
Sending MERGE lines with the new keys directly would **create duplicates**.
</details>

**S5. An Assignment line has no SourceSystemOwner/SourceSystemId (it uses AssignmentNumber), but references the job as `JobId(SourceSystemId) = JOB_SE01`. The load fails. Why?**
<details><summary>Answer</summary>

You **can't use source keys for foreign references unless the local record also uses a source key**. Either add a source key for the assignment, or reference the job by **user key** (`JobCode`, plus set code if needed) or by **surrogate ID** (`JobId`).
</details>

**S6. A new hire file and a new Job file are submitted in two separate zips at the same time. Some workers fail with "job not found". What happened?**
<details><summary>Answer</summary>

The job records **didn't exist yet** when those workers were processed. Source keys and other keys aren't recognised until the referenced record exists in Oracle. Fix: load the Job zip **first** (or put both `.dat` files in the **same zip** so HDL processes them in dependency order), then resubmit the failed workers.
</details>

**S7. Write a BIP SQL query to list all Location source keys loaded from owner `LEGACY` with their surrogate IDs and GUIDs.**
<details><summary>Answer</summary>

```sql
SELECT object_name,
       source_system_owner,
       source_system_id,
       surrogate_id,
       RAWTOHEX(guid) AS guid
FROM   hrc_integration_key_map
WHERE  source_system_owner = 'LEGACY'
AND    object_name         = 'Location';
```
</details>

**S8. Interview question: "Which key type would you recommend for a conversion project, and why?"**
<details><summary>Answer</summary>

**Source keys**, for every object and component. They:
- can be used for **both create and update**, so the same file can be rerun across mock cycles;
- are **portable** across DEV/TEST/PROD (unlike surrogate IDs);
- give **traceability** back to the legacy record;
- don't depend on business values like names that can change (unlike user keys).
Set them up with a documented naming convention, register the owner in `HRC_SOURCE_SYSTEM_OWNER`, and check them after each load through `HRC_INTEGRATION_KEY_MAP`.
</details>
